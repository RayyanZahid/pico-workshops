## The concept

You don't rebuild a site to make it spatial. You pick a few elements and give them a Z axis. WebSpatial's mental model is **"2D containing 3D"**: layout on X and Y is still plain CSS (flex, grid, `top`, `left`), and you add a small number of Z-axis properties on top. Every one of them is **ignored in an ordinary browser**, so the desktop site doesn't change.

The four moves of this level:

```
 before: one flat opaque panel          after: clear window, cards float on glass
 ┌───────────────────────────┐           ·  ·  ·  ·  ·  ·  ·  ·  ·  ·  ·     ← window glass:
 │ NAV                       │            ╔═══ NAV ═══╗   (enable-xr, back 20)   transparent
 │ ┌─────┐ ┌─────┐ ┌─────┐   │           ·                                ·
 │ │card │ │card │ │card │   │     →      ╔═════╗ ╔═════╗ ╔═════╗             ← cards: enable-xr,
 │ └─────┘ └─────┘ └─────┘   │           ·║glass║ ║glass║ ║glass║         ·     back 40, translucent
 │ [Learn more]              │            ╚═════╝ ╚═════╝ ╚═════╝
 └───────────────────────────┘           ·  [Learn more] ──window.open──► second window "details"
```

1. **Mark** the elements you want lifted with `enable-xr`.
2. **Lift** them with `--xr-back`.
3. **Glass**: make the window transparent and give lifted elements a translucent material.
4. **Split**: move secondary content into its own window.

## The key APIs, minimal

### 1. `enable-xr`: turn an element into a spatialized element

Three equivalent spellings, so it works with third-party components:

```tsx
<div className="card" enable-xr />
<div className="card __enableXr__" />
<div className="card" style={{ enableXr: true }} />
```

A spatialized element keeps its X/Y layout from CSS, becomes a plane floating in the scene, and automatically becomes a containing block (as if `position: relative`). Don't mark everything: each one is a separate native plane.

If a parent's children appear, disappear or resize and that moves a spatialized child, put `enable-xr-monitor` on the parent so the SDK re-syncs positions:

```tsx
<ul enable-xr-monitor>{items.map(i => <li key={i.id} enable-xr>{i.name}</li>)}</ul>
```

### 2. `--xr-back`: move along Z

```css
.card {
  position: relative;      /* required: relative, absolute or fixed */
  --xr-back: 40;           /* px only; "40px" also works; one decimal allowed */
}
```

- It's an **inset** property, like `top`, but on Z: the distance to the plane "behind" the element.
- With `relative`: that's the plane the element sat on before. With `absolute`: the nearest spatialized ancestor's plane, or the page. With `fixed`: always the page plane.
- Plain children move with a lifted parent.
- **Don't nest one `enable-xr` element inside another.** The docs say a nested one measures `--xr-back` from its spatial parent, but on PICO OS 6.0.0 nested spatial elements never rendered (empty 0×0 documents; VERIFIED 2026-09-24 in lab p4). Keep spatial elements top-level, and if you want "card in front of section", give the card the absolute depth.
- Units are **px (points)**, not metres. For metres, use `useMetrics()` (L3).

### 3. `--xr-background-material`: glass or clear

Values: **`translucent` | `transparent` | `none`** (default `none`).

```css
html  { --xr-background-material: transparent; }   /* the window: remove its opaque backplate */
.card { --xr-background-material: translucent; }   /* a lifted element: add a glass backplate */
```

On the window (`html`), `transparent` removes the panel so your elements float free, and `translucent` makes the whole panel glass. On an `enable-xr` element, `translucent` adds a glass backplate. It doesn't apply to `<Model>` or `<Reality>`.

For glass to show, **your own CSS background must not cover it**. If `body` or `.card` has an opaque `background`, you'll see the colour, not the glass. Make those backgrounds transparent (or semi-transparent) in spatial mode. The simplest switch is a class you add when `navigator.userAgent` matches `/WebSpatial\//`.

### 4. Spatial transform: tilt and push

Plain CSS `transform` gets real 3D on spatialized elements. `perspective()` and `transform-style` are ignored because they're not needed.

```css
.sidebar { position: fixed; left: 0; transform-origin: left center; transform: translateZ(80px) rotateY(20deg); }
```

`--xr-back` moves the layout position; `transform` moves only the visuals. **No CSS animations or transitions** on spatialized elements yet. To animate, update the style from JS (for example in `requestAnimationFrame`).

### 5. A second window

Any link or `window.open` to a URL inside your app's manifest scope opens a **new spatial scene**. Give it a name, and configure it with `initScene` *before* you open it:

```ts
import { initScene } from '@webspatial/react-sdk'

export function registerScenes() {
  initScene('details', prev => ({ ...prev, defaultSize: { width: 480, height: 600 } }), { type: 'window' })
}

export function openDetails() {
  window.open('/?scene=details', 'details')   // 2nd arg = scene name
}
```

**Gotcha: `initScene` before boot does nothing.** In SDK 2.0's lazy entry, `initScene` is `getSpatialImpl()?.getSession?.()?.initScene(...)`, so until `<SpatialBoot>` has booted it is a **silent no-op**. Calling it at module load (top of `main.tsx`) made lab p3's volume open as a default flat 1280×720 window. Register scenes in `onReady`, which runs after boot and before the children render:

```tsx
<SpatialBoot onReady={registerScenes} onError={(err) => console.error('WebSpatial boot failed', err)}>
  <Root />
</SpatialBoot>
```

*(VERIFIED 2026-09-24 in the emulator, emulator-lab on p3; SOURCE: `@webspatial/react-sdk` 2.0.0 `dist`. Every lab with scenes, p2 to p5, does this.)* Calling `initScene` inside a click handler is fine too, because by then the app has booted.

The scene **type goes in the third argument**, `{ type: 'window' | 'volume' }`, not inside the config object. Some webspatial.dev examples put `type` inside the returned config, but in SDK 2.0.0 the config type (`SpatialSceneCreationOptions`) has no `type` field, so TypeScript rejects it.

`defaultSize` numbers are px; strings can carry units (`"2m"`). The OS treats the size as a request, not a guarantee. On PICO OS 6.0.0 we observed second windows opening at the main window's size regardless of `defaultSize`. In a desktop browser the same call just opens a tab. Route `?scene=details` to a `Details` component in `main.tsx` (L4 covers routing properly).

## Common mistakes

- **Wrapping a second window's whole page in `enable-xr`.** On PICO OS 6.0.0 it came up blank (p4's HUD as one `<main enable-xr>`, p2's per-row schedule layers). In a second window, don't wrap the page in `enable-xr`; the window is already glass. Keep floating panels small and few (a large one intermittently fails to create on PICO OS 6.0.0). Observed OS behavior (PICO OS 6.0.0, 2026-09-24): second windows opened at the main window's size, in the main window's slot, regardless of the requested `defaultSize` (520×640 and 360×480 in the labs). The page doesn't control this.
- **A lifted card inside a lifted section.** On PICO OS 6.0.0 the nested one never renders. Make only one of them `enable-xr`, or un-nest them and give each an absolute `--xr-back`.
- **`initScene` at the top of `main.tsx`.** Before `<SpatialBoot>` boots it silently does nothing, and the scene opens at the default size. Register scenes in `onReady`.
- **`--xr-back` does nothing.** The element has no `position` (it needs relative, absolute or fixed), or it isn't marked `enable-xr`.
- **Writing `back` or `xr-back`.** It's a CSS custom property: `--xr-back`, with the two dashes.
- **Using metre units in `--xr-back`.** Only px. `"0.1m"` isn't valid here (it *is* valid in `defaultSize`).
- **Expecting `thin` / `regular` / `thick`.** The current SDK accepts only `translucent`, `transparent` and `none`.
- **Glass looks like a solid colour.** Your own `background` is painted on top. Clear it in spatial mode.
- **CSS `transition` on a lifted card.** Not supported yet; animate from JS.
- **Setting styles imperatively with `querySelector`.** Spatial styles and events only work through React (JSX props or refs). `document.querySelector('.card').style.setProperty('--xr-back', ...)` isn't supported.
- **`aspect-ratio` fighting a grid** inside a fixed-size window: it shows up as clipped content in the scene. Prefer `grid-template-rows: repeat(n, minmax(0, 1fr))`. (Seen in an SDK 1.x project.)
- **Opening an external URL** with `window.open`. Anything outside the manifest scope opens in the browser, not as a scene.

## Check your understanding

1. **You set `--xr-back: 40` on a card and nothing moves. Name two likely causes.**
   No `enable-xr` marker, or no `position: relative|absolute|fixed`. (A third: the page is in a browser tab instead of the installed Web App, so no runtime.)
2. **What's the difference between `--xr-back: 40` and `transform: translateZ(40px)`?**
   `--xr-back` changes the element's Z layout position, and children and event coordinates follow it. `translateZ` changes only where it's drawn, relative to that layout position.
3. **Which values does `--xr-background-material` accept, and where do you put it to make the window disappear?**
   `translucent`, `transparent`, `none`. Put `transparent` on `html`.
4. **You call `window.open('/details', 'details')` but the new window is the wrong size. What did you forget?**
   Registering `initScene('details', …)` with a `defaultSize` **after boot and before** `window.open`, i.e. in `<SpatialBoot onReady={registerScenes}>`. A call at module load is a silent no-op in SDK 2.0. The name must match the second argument.
5. **Does any of this change what a desktop visitor sees?**
   No. `enable-xr`, `--xr-*` and `initScene` are ignored or no-ops outside a WebSpatial runtime, and `window.open` opens a normal tab.
