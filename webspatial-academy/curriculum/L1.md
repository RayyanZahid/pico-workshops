## The concept

A normal website lives inside a browser tab, which is a rectangle on a screen. On a spatial computer, the OS arranges apps in the room around you. **WebSpatial lets a website become one of those apps**: its pages become windows floating in space, parts of a page can lift off toward you, and a page can hold real 3D objects. It does this with a few additions to HTML, CSS and the DOM, so you keep writing a website.

That's different from **WebXR**. WebXR hands your page a canvas and a head pose, and you draw every pixel of an immersive world yourself (three.js, A-Frame). WebSpatial hands the OS your *HTML* and lets the OS render it next to other apps, with native materials and gestures.

| | WebXR | WebSpatial |
|---|---|---|
| You write | a 3D renderer on a canvas | HTML + CSS + a few 3D components |
| Runs | inside one immersive session that takes over the view | as windows and volumes in the shared space, next to other apps |
| Multiple windows | no | yes, each `window.open` is a new spatial window |
| Needs | any WebXR browser | a WebSpatial runtime (PICO OS 6; visionOS via packaging) |

### Windows and volumes

Every page of a WebSpatial app opens in a **Spatial Scene**. There are two kinds:

```
   window scene                         volume scene
 ┌──────────────────┐               ┌──────────────────┐
 │  2D page plane   │  ← GUI        /│  back face = page│ ← real depth (metres)
 │  (can be glass   │    stays     / │                  │   scales with distance
 │   or clear)      │    readable ┌──────────────────┐ │   like a real object
 │   ▢ ▢  lifted    │             │   3D content     │ │
 │   elements float │             │   lives in here  │/
 └──────────────────┘             └──────────────────┘
```

- **window** (default): a 2D panel for GUI. It keeps the same apparent size as you move it, so text stays readable.
- **volume**: a box with real depth, for showing an object. It shows distance-based scaling by default, like a real thing would.

### React is required (plainly)

**WebSpatial currently requires React. There is no plain-HTML path.** The SDK works by plugging into React's **JSX runtime**. When you set `jsxImportSource` to `@webspatial/react-sdk`, every `<div>` you write in JSX goes through WebSpatial's version of `createElement`, which is what understands `enable-xr` and `--xr-back`. A static `.html` file never goes through JSX, so the markers do nothing there. If your site isn't React, the smallest path is to wrap it in a Vite + React shell and move the parts you want to spatialize into components (that's what L5's capstone does).

### How it runs on PICO: browser tab = flat, Web App Runtime = spatial

This is the single most important fact of the course. PICO OS 6 has **two** ways to show your page, and WebSpatial only works in one of them:

```
  PICO Browser tab                         PICO OS 6 Web App Runtime
 ┌─────────────────────────────┐          ┌─────────────────────────────┐
 │ ◀ ▶ localhost:5301  [🖥]☆  │ Install  │   your page, its own glass  │
 │   monitor icon ─┘           │ ───────► │   window  ▢ lifted ▢ lifted │
 │  your page, FLAT            │          │   window.open = new window  │
 │  (WebSpatial APIs inert)    │          │  (WebSpatial APIs ACTIVE)   │
 └─────────────────────────────┘          └─────────────────────────────┘
```

PICO's docs: *"In the Web App Runtime of PICO OS 6, any WebSpatial API used in your page source is automatically activated."* An ordinary browser tab isn't the Web App Runtime, so the same page is flat there. **(DOC, developer.picoxr.com/document/web/webspatial/)**

## The key APIs, minimal

**1. Install** (SDK 2.x):

```bash
npm create vite@latest hello-spatial -- --template react-ts
cd hello-spatial
npm i @webspatial/react-sdk@2.0.0 @webspatial/core-sdk@2.0.0 --save-exact
```

**2. Route JSX through the SDK:** `tsconfig.app.json` (the tsconfig that holds `"jsx"`):

```json
{
  "compilerOptions": {
    "jsx": "react-jsx",
    "jsxImportSource": "@webspatial/react-sdk"
  }
}
```

…and **also** on the React plugin in `vite.config.ts`, because Vite 8 compiles JSX with oxc and doesn't take the setting from tsconfig or `esbuild`. The labs set it in both places:

```ts
// vite.config.ts
plugins: [react({ jsxImportSource: '@webspatial/react-sdk' })]
```

**Without this line, `enable-xr` silently does nothing**: the build compiles with React's plain JSX runtime, TypeScript is happy, nothing errors, and no element ever lifts.

**3. Boot it:** `src/main.tsx`:

```tsx
import { createRoot } from 'react-dom/client'
import { SpatialBoot } from '@webspatial/react-sdk'
import App from './App'

createRoot(document.getElementById('root')!).render(
  <SpatialBoot>
    <App />
  </SpatialBoot>,
)
```

`<SpatialBoot>` loads the spatial half of the SDK only when it's running inside a WebSpatial runtime. In a desktop browser it just renders your app. It shows **nothing** while it loads, and it has no `fallback` prop, so put any loading UI outside it.

**4. A minimal PWA manifest:** `public/app.webmanifest`, linked from `index.html` with `<link rel="manifest" href="/app.webmanifest" />`:

```json
{
  "name": "Hello Spatial",
  "start_url": "/",
  "display": "minimal-ui",
  "icons": [
    { "src": "/pwa-512x512.png",   "sizes": "512x512",   "type": "image/png", "purpose": "any" },
    { "src": "/pwa-1024x1024.png", "sizes": "1024x1024", "type": "image/png", "purpose": "maskable" }
  ]
}
```

PICO requires **four** fields: `name` (or `short_name`), `icons`, `start_url` and **`display`**. `display` is mandatory on PICO, not optional as on some platforms, and WebSpatial supports `standalone` or `minimal-ui`. The manifest URL must return a **JSON MIME type** such as `application/manifest+json` (Vite serves `.webmanifest` from `public/` correctly; a custom server may not). `scope` decides which URLs belong to the app, and so whether the Install app icon appears. The 1024 maskable icon is the spatial app icon: no transparency and no rounded corners. Use **PNG icons with real `sizes`**: a manifest with a single SVG icon at `sizes: "any"` was rejected by the OS web-app check (`DiscernWebApp: onGotManifestDataError`), and the lab manifests with 192/512/1024 PNGs pass (the SVG as the cause is INFERRED, `assets/emulator/WALKTHROUGH.md`). On an `http://` dev server the installed app's icon is a generic placeholder, because the installer won't fetch it over cleartext. That's cosmetic. **(DOC, developer.picoxr.com/document/web/manifest/ + webspatial.dev Minimal PWA)**

**5. Let the emulator reach the dev server:** `vite.config.ts`:

```ts
export default defineConfig({
  plugins: [react({ jsxImportSource: '@webspatial/react-sdk' })],
  server: { host: true, port: 5301 },   // the labs run `vite --host 0.0.0.0 --port 530n` via npm run dev:xr
})
```

**6. Your first spatial element:**

```tsx
export default function App() {
  return (
    <main>
      <h1>Hello, space</h1>
      <p enable-xr style={{ position: 'relative', '--xr-back': 60 } as React.CSSProperties}>
        I float 60px in front of the page.
      </p>
    </main>
  )
}
```

**7. How do I know I'm in the runtime?** Two checks, and a good lab page shows both as a badge:

```ts
// PICO's documented check: browser tab vs Web App Runtime (DOC, /document/web/install-free/)
const mode = matchMedia('(display-mode: browser)').matches ? 'browser tab (flat)'
  : matchMedia('(display-mode: standalone)').matches || matchMedia('(display-mode: minimal-ui)').matches
    ? 'Web App (spatial)' : 'unknown'

// Which runtime (DOC, webspatial.dev userAgent): PicoWebApp/<ver> = PICO OS 6 Web App Runtime,
// WebSpatial/<ver> = a WebSpatial runtime is present
const ua = navigator.userAgent
```

It also works in CSS: `@media (display-mode: standalone) { … }`. If the badge says "browser tab", nothing will pop out, and that's the reason.

## Common mistakes

- **#1: No `<SpatialBoot>`.** In SDK 2.0 the spatial code is loaded **only** inside `<SpatialBoot>`. Without it, `enable-xr`, `--xr-*` and the 3D components stay inert even inside the installed Web App, with no error anywhere. Wrap the root once.
- **`jsxImportSource` in only one place, or the wrong tsconfig.** It goes in the tsconfig that holds `"jsx"` (Vite's template splits `tsconfig.json` / `tsconfig.app.json` / `tsconfig.node.json`) **and** on `react({ jsxImportSource })` in `vite.config.ts`. With only the tsconfig set, the Vite 8 build can silently use React's plain runtime. If `<SpatialBoot>` is there and the markers still do nothing, suspect this next.
- **Adding a WebSpatial build plugin from a 1.x tutorial.** SDK 2.0 needs none. The Academy uses plain `@vitejs/plugin-react`: one bundle for every platform, with the runtime detected from the user agent. (See [TROUBLESHOOTING, version drift](TROUBLESHOOTING.md#version-drift).)
- **Hunting for an `is-spatial` class or `XR_ENV` on `window.__webspatialsdk__`.** The SDK adds no class to `<html>`. The labs add their own `is-spatial` class after testing `navigator.userAgent` against `/WebSpatial\//`. `window.__webspatialsdk__` reports SDK versions (`react-sdk-version`), not an `XR_ENV`.
- **Staying in the browser tab.** The page loads, looks fine, and nothing lifts. In a PICO Browser tab WebSpatial is inert by design; you must **install it** (monitor icon left of the star → Install), then wait up to 60 s; if panels are still missing, close and reopen the app once. Check the display-mode badge.
- **Opening `http://10.0.2.2:<port>/`** (what PICO's docs and `pico-cli web launch` do). The page loads but isn't a secure context, so it can't be installed or opened as a Web App and stays flat. Use `adb reverse tcp:<port> tcp:<port>` + `http://localhost:<port>/`.
- **`http://localhost:<port>` without `adb reverse`.** Inside the guest, `localhost` is the emulator itself, so you get connection refused.
- **No manifest, or an invalid one.** No button without a manifest that has `name`/`short_name`, `icons`, `start_url` and `display`, served with a JSON MIME type, and a `scope` covering the URL.
- **Running `npm run dev` instead of `npm run dev:xr`.** Plain `dev` may bind only IPv6 `::1`, which `adb reverse` can't reach. `dev:xr` binds `0.0.0.0`.
- **Expecting effects in the desktop browser.** In Chrome your page is supposed to look like a normal page. That's the fallback working.
- **Mixing 1.x instructions.** Old guides and SDK 1.x projects use `XR_ENV=avp`, a `/webspatial/avp/` dev URL, and imports from `@webspatial/react-sdk/web` or `/default`. None of that exists in 2.x.
- **Blank page inside the emulator, fine on desktop.** `<SpatialBoot>` hides children until boot finishes, and forever if boot fails. Add `onError={e => console.error(e)}` and read it in DevTools (see [TROUBLESHOOTING](TROUBLESHOOTING.md)).
- **Styled-components.** Currently unsupported by the SDK (a known bug per the docs).

## Check your understanding

1. **Can you add WebSpatial to a static `index.html` with a `<script>` tag?**
   No. The SDK is React-only and works through the JSX runtime. Without JSX there's nothing to intercept `enable-xr` or `--xr-*`.
2. **What's the difference between a window scene and a volume scene?**
   A window is a 2D panel for GUI that keeps a constant apparent size. A volume has depth, simulates a physical object, and scales with distance by default.
3. **What three things turn a React + Vite app into a WebSpatial app on PICO?**
   `jsxImportSource: "@webspatial/react-sdk"`, a `<SpatialBoot>` wrapper, and a valid PWA manifest. Plus `server.host: true` so the emulator can reach it.
4. **Your page looks totally normal in Chrome. Is that a bug?**
   No. WebSpatial styles and markers are ignored outside a WebSpatial runtime, and `<SpatialBoot>` skips loading the spatial code. That's progressive enhancement.
5. **Why don't you need to package the app for PICO OS 6?**
   The OS's Web App Runtime already contains the WebSpatial runtime, so a URL is enough. visionOS doesn't, which is why it needs the Builder.
