Each row writes its **absolute** depth: `(5 + y × 0.08) + row × 20 + flinch`. Nothing is nested. At wave 1 (y = 80) the front row is 11.4 + 80 = **91.4 px**. **Keep depths modest:** planes lifted far toward you, low in the window, fall below it.

::: notes
Start y is 80 (solution/src/constants.ts START_Y), per wave +14 up to wave 5. Numbers from labs/p4-space-invaders/README.md "The depth map (solution)" and solution/src/depth.ts: rows ROW_STEP 20, formation 5 + y × 0.08, shields 100, ship 120 (the deepest the front row ever reaches is 5 + 412 × 0.08 + 80 = 118), flinch 24 with POP_DECAY 0.85 (about 200 ms), overlay card 150 while shown, buttons flat. The first version used ship 260, shields 210 and 30 px steps, and in the emulator's default view the ship and buttons projected below the window's bottom edge. All values are px, one decimal, never negative, written through refs by writeBack(el, z), which skips unchanged values.
:::

=== L4-s3 concept
# The layer budget: 11 planes, not 230+
img: ../assets/emulator/25-lab4-angled-rows-in-depth.png | Lab 4 from the side in the emulator: each invader row stands at its own depth off the window, and the shields float out in front (captured with the earlier, deeper settings)
lead: Each enable-xr element is its own native plane. Spatialize containers, not sprites.

| Layer | Planes | Depth (px) |
|---|---|---|
| Rows 0 to 4 | 5 | `(5 + y × 0.08) + row × 20` |
| Invaders (55) | **0** | ride on their row |
| Shields | 1 | 100: four bunkers on one plane |
| Ship | 1 | 120, always the closest |
| Shots, bombs | 4, pooled | travel in Z |
| ◀ Fire ▶ | **0** | flat on the window; pinch = click |
| Playfield | **0** | plain div: no nesting |

**11 planes** (12 with the overlay card) vs **230+** if every sprite were spatial.

::: notes
The key lesson of the level. The docs publish no per-scene plane limit, so treat roughly 15 as a budget habit, not a hard number; measure it with pico-cli perf in L5. The UFO stays on the page plane plane (cosmetic, 0 planes). Unverified on the emulator: frame rate with per-frame --xr-back writes.
:::

```prompt
Make the ship (120) and the shield line (100) enable-xr at fixed depths, and the 2 pooled shots and 2 pooled bombs enable-xr. ```
```

::: notes
The on-screen ◀ Fire ▶ buttons use plain onClick: a pinch on a spatial button arrives as a click. Never put onSpatialTap on a <button>, even gated by useSpatialReady(): inside the PICO runtime it logs "Unknown event handler property onSpatialTap". === L4-s9 step
# Gotcha: a message posted just before window.open can vanish
action: Post first, then open the new window on a later task.

```code
// broken: same task, the HUD misses it
bus.post({ type: 'gameover', score, wave })
openScene('halloffame')

// fixed: open the new window on a later task
bus.post({ type: 'gameover', score, wave })
window.setTimeout(() => openScene('halloffame'), 100)
```

img: ../labs/_shots/p4-solution-halloffame.png | The hall of fame window in desktop Chrome, opened when the game ends: rank 1, score 130, wave 1

::: notes
In desktop Chrome, a BroadcastChannel message posted in the same task that opens a brand-new window was dropped for the windows already listening. The lab's automated check reproduces it: with the first form, the HUD never shows "Game over". Measured 2026-09-24 in Chrome with SDK 2.0.0; not yet measured inside PICO's web-app runtime, so keep the deferral either way.
:::
